Sì. La imposterei come una **specifica tecnica preliminare**, separando chiaramente ciò che possiamo riutilizzare da BitChat/NOMAD da ciò che deve essere progettato ex novo.

Il punto fondamentale è che **non costruirei una semplice fork di BitChat**: userei BitChat come riferimento per il *transport/mesh layer* e NOMAD come riferimento per il *local service/content layer*, introducendo un nuovo livello intermedio di **Offline Network Fabric**.

Di seguito una prima specifica abbastanza dettagliata da poter diventare la base del progetto.

# Specifica progettuale — Offline Internet Mesh

**Nome provvisorio:** NOMAD Mesh
**Codename:** `NOMAD-NET`
**Tipo:** rete distribuita offline-first, multi-transport, content-centric
**Stato:** concept / technical specification v0.1

---

## 1. Visione

NOMAD-NET è una rete di comunicazione distribuita progettata per fornire **contenuti, servizi e comunicazione digitale senza dipendere da Internet**.

La rete è composta da:

* smartphone;
* computer;
* server NOMAD;
* Raspberry Pi / mini-PC;
* eventuali gateway radio;
* altri dispositivi compatibili.

Ogni dispositivo può agire contemporaneamente come:

* client;
* server;
* relay;
* cache;
* router;
* content provider;
* gateway verso Internet.

La rete deve poter funzionare anche quando è:

* completamente isolata da Internet;
* fisicamente frammentata;
* caratterizzata da connessioni intermittenti;
* composta da dispositivi mobili;
* soggetta a elevata perdita di pacchetti.

Quando un nodo dispone di Internet, può diventare un **gateway di sincronizzazione**, importando contenuti e successivamente propagandoli nella rete.

---

# 2. Concetto fondamentale

L'architettura deve essere distinta in quattro livelli.

```text
┌──────────────────────────────────────────┐
│             APPLICATION LAYER            │
│                                          │
│ Web · Chat · Files · Maps · Search · AI  │
├──────────────────────────────────────────┤
│             SERVICE / CONTENT             │
│                                          │
│ NOMAD · Kiwix · Kolibri · RAG · Apps     │
├──────────────────────────────────────────┤
│           OFFLINE NETWORK FABRIC         │
│                                          │
│ Discovery · Routing · Cache · Sync       │
│ Replication · Store & Forward            │
├──────────────────────────────────────────┤
│              TRANSPORT LAYER             │
│                                          │
│ BLE · Wi-Fi Direct · Wi-Fi LAN · LoRa    │
│ Ethernet · Internet                      │
└──────────────────────────────────────────┘
```

La separazione è fondamentale.

BitChat attualmente implementa già diversi concetti utili nel transport/mesh layer: BLE mesh, controlled flooding, TTL, deduplicazione, source routing, frammentazione, store-and-forward e courier mechanism. ([GitHub][1])

Project NOMAD fornisce invece il modello di **server offline con contenuti, AI, database e applicazioni locali**.

Il nuovo progetto deve collegare questi due mondi.

---

# 3. Obiettivo

L'utente deve poter accedere a servizi e contenuti senza sapere:

* dove si trova il server;
* quale dispositivo possiede il contenuto;
* quale protocollo radio viene utilizzato;
* quanti hop sono necessari;
* se il contenuto è originale o una copia;
* se il nodo è temporaneamente offline.

L'esperienza deve essere simile a:

```text
Internet
```

ma l'infrastruttura sottostante è:

```text
device → mesh → cache → server → mesh
```

---

# 4. Differenza rispetto a Internet

NOMAD-NET **non deve tentare di replicare TCP/IP/Internet in modo trasparente**.

Il modello è invece **content-centric**.

L'applicazione non dovrebbe chiedere:

```text
GET 192.168.1.42/wiki/italia
```

ma:

```text
GET content://wikipedia/it/italia
```

oppure:

```text
GET service://search
```

oppure:

```text
GET service://translation
```

La rete decide autonomamente:

1. se esiste una copia locale;
2. quale nodo possiede il contenuto;
3. quale percorso utilizzare;
4. quale transport utilizzare;
5. se utilizzare una cache;
6. se aspettare una futura connessione.

---

# 5. Identità dei contenuti

Ogni risorsa deve avere un identificatore stabile.

Esempio:

```text
content_id =
SHA-256(canonical_content)
```

oppure un CID compatibile con un sistema content-addressed.

Esempio:

```text
cid:
bafybeigd...
```

Questo permette di verificare automaticamente l'integrità.

Un nodo può quindi annunciare:

```text
NODE A

content:
    wikipedia/it/*
    maps/lombardia/*
    books/italian/*
```

ma non deve necessariamente trasferire l'intero catalogo.

```text

```

# 7. Discovery distribuito

Non deve esistere un DNS centrale.

Il discovery deve essere distribuito.

Possibili meccanismi:

### 7.1 Local advertisement

Il nodo comunica periodicamente:

```text
I provide:

content A
content B
service C
```

### 7.2 Query flooding controllato

```text
Alice
 ↓
Bob
 ↓
Charlie
 ↓
NOMAD
```

### 7.3 Distributed catalog

I nodi possono conservare una piccola cache:

```text
content_id → known providers
```

con TTL.

### 7.4 Opportunistic discovery

Quando due dispositivi si incontrano:

```text
A ↔ B
```

possono scambiarsi:

```text
capabilities
known content
known services
network information
```

senza trasferire i contenuti.

# 9. Transport Manager

Il nodo deve poter gestire più transport.

### Transport previsti

**MVP**

* BLE

**v1**

* Wi-Fi Direct
* Wi-Fi LAN

**v2**

* Ethernet
* LoRa gateway

**v3**

* Internet gateway

Ogni transport implementa una API comune:

```typescript
interface Transport {
    id: string;

    start(): Promise<void>;
    stop(): Promise<void>;

    discover(): Promise<Peer[]>;
    connect(peer: Peer): Promise<Connection>;

    send(
        peer: Peer,
        packet: Packet

    getCapabilities(): TransportCapabilities;
}
```

# 13. Routing

Il routing è uno degli elementi principali da progettare ex novo.

BitChat attualmente usa una combinazione di controlled flooding e source routing, con TTL, deduplicazione e informazioni sui vicini. ([GitHub][1])

Per NOMAD-NET servirebbe però un routing **content/service-aware**.

Un percorso non deve essere valutato solamente in base alla distanza.

Deve considerare:

```text
hop count
bandwidth
latency
battery
signal quality
packet loss
storage
content availability
transport
node reliability
```

Una funzione di costo potrebbe essere:

```text
Cost =
    α × hops
  + β × latency
  + γ × loss
  + δ × energy
  + ε × congestion
```

con parametri configurabili.

---

# 14. Store & Forward

È un componente fondamentale.

Se:

```text
Alice → X
```

ma X non conosce Bob, il messaggio non viene necessariamente perso.

Può essere memorizzato:

```text
Alice
 ↓
Courier A
 ↓
Courier B
 ↓
Bob
```

BitChat implementa già un modello di store-and-forward con outbox persistente, courier e spray-and-wait. ([GitHub][1])

NOMAD-NET dovrebbe generalizzare questo meccanismo dai **messaggi** ai **contenuti e task**.

# 15. Content replication

Questo è uno dei concetti centrali.

Se un contenuto viene richiesto frequentemente:

```text
NOMAD A
   ↓
100 richieste
```

il sistema può decidere di replicarlo:

```text
NOMAD A
   ↓
NOMAD B
   ↓
NOMAD C
```

La replica può essere:

### Manuale

L'utente sceglie:

> Mantieni sempre disponibile Wikipedia Italia.

### Automatica

Il sistema rileva:

```text
high demand
```

e replica il contenuto.

### Opportunistica

Un dispositivo conserva automaticamente contenuti che incontra frequentemente.

# 16. Cache

Ogni nodo può avere:

```text
L1 cache
```

contenuti temporanei.

Esempio:

```text
MAX CACHE = 10 GB
TTL = 7 giorni
```

Replacement policy:

```text
LRU
+
popularity
+
network scarcity
```

Un contenuto raro potrebbe avere maggiore priorità di conservazione rispetto a uno facilmente reperibile.

# 17. Network topology

La rete deve supportare contemporaneamente:

### Dense mesh

```text
A ─ B ─ C
│ ╲ │ ╱ │
D ─ E ─ F
```

### Sparse mesh

```text
A ─ B ─ C ─ D ─ E
```

### Partitioned network

```text
A ─ B ─ C          D ─ E ─ F
```

Le due reti possono successivamente incontrarsi:

```text
A ─ B ─ C          D ─ E ─ F
        ╲          ╱
         ──── X ───
```

X sincronizza le informazioni.

---

# 18. Network synchronization

Quando due network precedentemente separate si incontrano:

```text
Mesh A
   │
   X
   │
Mesh B
```

non devono sincronizzare tutto.

Devono prima confrontare:

```text
content catalogs
service catalogs
message indexes
version vectors
```

e trasferire solamente ciò che manca.

Questo richiede un meccanismo simile a:

```text
Merkle tree
Bloom filter
GCS filter
version vector
```

BitChat utilizza già GCS filters per la sincronizzazione della cronologia pubblica. ([GitHub][1])

# 19. Internet Gateway

Un nodo può dichiararsi:

```text
INTERNET_GATEWAY
```

Il gateway diventa il punto di sincronizzazione con Internet.

Esempio:

```text
                 INTERNET
                    │
              ┌─────┴─────┐
              │  Gateway  │
              └─────┬─────┘
                    │
                  Mesh
              ┌─────┼─────┐
              │     │     │
             A      B      C
```

Può:

* scaricare contenuti;
* aggiornare database;
* sincronizzare messaggi;
* aggiornare software;
* recuperare nuove mappe;
* sincronizzare AI models;
* esportare dati.

# 20. Delay-Tolerant Internet

Questo introduce un concetto importante:

**DTN — Delay Tolerant Networking.**

Una richiesta può non avere risposta immediata.

Esempio:

```text
USER
"Dammi la Wikipedia aggiornata"

        ↓

NETWORK

        ↓

"Content unavailable"

        ↓

STORE REQUEST

        ↓

3 ore dopo

        ↓

GATEWAY INTERNET

        ↓

DOWNLOAD

        ↓

MESH SYNC

        ↓

USER
```

La rete non fallisce necessariamente.

Può rispondere:

```text
REQUEST ACCEPTED
STATUS: PENDING
```

e notificare successivamente:

```text
CONTENT AVAILABLE
```

# 23. Sicurezza

La rete deve essere **zero-trust**.

Un relay non deve poter leggere il contenuto di una comunicazione privata.

Architettura:

```text
Sender
  │
  │ encrypt
  ▼
Relay
  │
  │ opaque packet
  ▼
Relay
  │
  ▼
Receiver
  │
  │ decrypt
  ▼
Plaintext
```

BitChat utilizza attualmente Noise per le sessioni mesh e primitive Curve25519/ChaCha20-Poly1305/SHA-256; questo rappresenta un riferimento concreto per il security layer. ([GitHub][1])

```text

```


# 26. Content authenticity

Un contenuto distribuito deve poter essere verificato.

Ogni contenuto può avere:

```text
content_id
version
publisher
signature
hash
timestamp
expiry
```

Il nodo ricevente verifica:

```text
hash(content) == content_id
```

e:

```text
signature == valid
```

prima di considerarlo attendibile.

# 27. Privacy

Bisogna distinguere:

### Public content

Può essere replicato liberamente.

### Private content

Cifrato per utenti autorizzati.

### Private messages

End-to-end encrypted.

### Sensitive metadata

Ridurre:

* identificatori persistenti;
* posizione;
* cronologia dei contatti;
* contenuti richiesti.

Il fatto che un nodo sia vicino fisicamente è comunque difficilmente occultabile quando si usa radio locale.

# 34. Esempio più avanzato

NOMAD non possiede la risorsa.

Ma dispone di Internet.

Riceve:

```text
CONTENT_QUERY
```

e risponde:

```text
PENDING
```

Scarica il contenuto.

Lo firma/verifica.

Lo memorizza.

Poi:

```text
SYNC
```

propaga il nuovo content ID.

La risorsa diventa disponibile a tutta la mesh.

Questa è la parte che rende il sistema realmente simile a una **Internet intermittente**.

### Scenario D — mobility

```text
A → B → C
```

B si sposta e porta il contenuto verso C.

### Scenario E — gateway intermittente

```text
Internet
   │
Gateway
   │
Mesh
```

gateway offline per 24 ore.

### Scenario F — network congestion

100+ dispositivi.

### Scenario G — malicious node

Un nodo:

* modifica contenuti;
* droppa pacchetti;
* genera flood;
* pubblicizza dati falsi.

Il sistema deve continuare a funzionare.

## 42. Definizione sintetica del progetto

La definizione che userei nella specifica ufficiale è:

> **NOMAD-NET è una rete distribuita, content-centric e delay-tolerant che permette a dispositivi mobili e nodi edge di condividere contenuti, servizi e comunicazioni senza infrastruttura Internet, utilizzando una combinazione di mesh locali, store-and-forward, caching opportunistico, replica distribuita e gateway intermittenti verso Internet.**

La parte più importante, a livello progettuale, è che **non cercherei di creare una nuova Internet basata su IP**. Creerei un **substrato distribuito di risorse e servizi**, sopra il quale è poi possibile costruire un'esperienza simile al Web.

Questa impostazione permette anche di partire relativamente piccolo: **BitChat/BLE → content discovery → NOMAD → cache → Wi-Fi → DTN → gateway Internet**, invece di dover progettare subito un'intera infrastruttura di rete.

Sì. I casi d'uso più interessanti non sono necessariamente quelli in cui "Internet manca", ma quelli in cui **una rete locale autonoma è più utile di Internet**.

# Criticità tecniche

## 1. Banda

**Problema principale.**

BLE è ottimo per:

* discovery;
* messaggi;
* piccoli metadata.

È pessimo per:

* video;
* grandi file;
* database;
* modelli AI.

**Soluzione:** architettura multi-transport, con Wi-Fi per il traffico pesante.

---

## 2. Portata

BLE introduce una topologia molto dinamica.

Un dispositivo che si sposta modifica continuamente la rete.

Serve quindi un routing estremamente robusto.

---

## 3. Battery drain

Il telefono non può:

```text
scansionare BLE
+ fare relay
+ mantenere connessioni
```

continuamente senza conseguenze.

Serve un **energy-aware networking**.

---

## 4. NAT e networking mobile

Wi-Fi Direct, Wi-Fi Aware, hotspot e LAN hanno comportamenti molto diversi tra:

* Android;
* iOS;
* Windows;
* Linux.

La compatibilità cross-platform può essere uno dei problemi più difficili.

---

## 5. iOS

È una criticità specifica.

Apple impone importanti restrizioni al comportamento Bluetooth/background delle app.

Quindi il modello:

> "ogni iPhone è sempre un router mesh"

potrebbe non essere realisticamente garantibile.

Potrebbe essere necessario che i nodi infrastrutturali facciano il grosso del lavoro.

---

## 6. Routing

Il routing classico non basta.

La rete deve sapere:

```text
chi ha il contenuto?
```

oltre a:

```text
come raggiungerlo?
```

Questo aumenta molto la complessità.

---

## 7. Discovery

Se la rete cresce a:

```text
10 nodi → semplice
100 → gestibile
1.000 → difficile
10.000 → problema serio
```

Il flooding indiscriminato diventerebbe rapidamente inefficiente.

Servono cataloghi, TTL, probabilistic discovery e caching.

---

## 8. Sincronizzazione

Due reti possono rimanere separate per giorni.

Quando finalmente si incontrano:

```text
Mesh A
   │
   X
   │
Mesh B
```

non è possibile trasferire semplicemente "tutto".

Servono:

* Merkle trees;
* version vectors;
* content hashes;
* deduplicazione;
* prioritizzazione.

---

## 9. Storage

Il sistema può generare enormi quantità di dati.

Bisogna decidere:

> cosa vale la pena conservare?

Una strategia puramente LRU potrebbe non essere sufficiente.

---

## 10. Sicurezza

Un nodo malevolo potrebbe:

* modificare contenuti;
* impersonare un server;
* pubblicizzare dati falsi;
* fare packet flooding;
* consumare le risorse degli altri nodi;
* intercettare metadata.

Serve una struttura **zero-trust + autenticazione crittografica**.

---

## 11. Spam / abuso

Una rete senza Internet non significa automaticamente una rete sicura.

Un dispositivo potrebbe generare:

```text
1.000.000 richieste
```

e saturare la mesh.

Servono:

* rate limiting;
* reputation;
* quotas;
* priority;
* admission control.

---

## 12. Content authenticity

Il fatto che un contenuto sia disponibile non significa che sia autentico.

Esempio:

```text
"Evacuazione zona X"
```

potrebbe essere falso.

Servono firme digitali e publisher verificati per i contenuti critici.

---

## 13. Incentivi

Probabilmente uno dei problemi **più sottovalutati**.

Perché il telefono di un utente dovrebbe:

* fare relay?
* consumare batteria?
* occupare storage?
* trasferire dati per altri?

Per una rete spontanea servono meccanismi di:

* opt-in;
* limiti energetici;
* priorità;
* eventuale reputazione.

---

## 14. Densità della rete

Una mesh funziona bene solo se esistono abbastanza nodi.

Questo genera un problema di bootstrap:

> Se non ci sono nodi, la rete non esiste.

Per questo i **NOMAD node fisici** potrebbero essere molto più importanti degli smartphone.

# Il caso d'uso che vedo più forte

Non partirei dal concetto generico di "Internet offline".

Partirei da:

> **NOMAD Network: una rete locale autonoma di contenuti e servizi, capace di funzionare senza Internet e di sincronizzarsi con Internet quando disponibile.**

E costruirei il primo prototipo per **rifugi / trekking / emergenze**.

È un ambiente ideale perché combina:

* assenza di connettività;
* necessità reale di informazioni;
* piccole comunità;
* contenuti prevalentemente statici;
* valore elevato delle mappe;
* possibilità di installare nodi fisici;
* tolleranza a latenze elevate;
* forte utilità dello store-and-forward.

Da lì la stessa tecnologia può scalare verso **emergenze, comunità remote, eventi, scuole e infrastrutture critiche**.

Partirei molto più semplicemente della specifica completa. L'obiettivo dei primi 10 step deve essere **dimostrare che l'idea funziona**, non costruire subito la rete definitiva.

```typescript
  | "ACK";
```

Ogni pacchetto:

```typescript
interface Packet {
  id: string;
  type: MessageType;
  source: string;
  destination?: string;
  ttl: number;
  timestamp: number;
  payload: unknown;
}
```

Per ora JSON.

Non binario.

Non CBOR.

Non protobuf.

**Prima facciamo funzionare il concetto.**

2. creano una rete;

# Cos'è fisicamente un Gateway?

Il **gateway non è un componente obbligatorio né un dispositivo specifico**.

È semplicemente un dispositivo che ha **due mondi collegati contemporaneamente**.

Esempio:

```
        INTERNET
            │
            │
        Gateway
            │
       Nomad-Net
            │
     ┌──────┼──────┐
     │      │      │
    PC    Phone   Phone
```

Il gateway è il "ponte".

Ha una connessione verso:

* Internet;
* rete Nomad-Net.

---

## Quindi un gateway può essere:

### Caso 1 — Un computer portatile

Il caso più semplice per iniziare.

Esempio:

```
MacBook
│
├── Internet tramite Wi-Fi
│
└── Nomad-Net tramite Bluetooth/Wi-Fi Direct
```

Il MacBook esegue:

```
nomad-gateway
```

e fa da ponte.

Questo è probabilmente il primo gateway che useresti.

---

### Caso 2 — Uno smartphone

Sì, teoricamente anche uno smartphone può essere un gateway.

Esempio:

```
iPhone
│
├── 4G/5G
│
└── Bluetooth mesh
```

Riceve una richiesta dalla mesh:

> "Cerco Wikipedia Italia"

e la inoltra tramite Internet.

Problema:

* iOS limita molto le attività in background;
* mantenere un telefono sempre disponibile come router è difficile;
* consuma batteria.

Su Android è più fattibile.

---

### Caso 3 — Un server fisso

È il caso ideale per una rete reale.

Esempio:

```
Casa / Rifugio / Scuola

Internet
   │
   │
Computer acceso
   │
Nomad-Net
   │
Utenti locali
```

Può essere:

* un vecchio PC;
* un mini PC;
* un NAS;
* un Raspberry;
* un server.

---

# Nel tuo progetto Nomad-Net cosa farei?

Non introdurrei subito il concetto di gateway.

```
    │
    │

    │
    │
Computer C
```

Obiettivo:

## Fase 2 — Introduciamo un "Nomad Node"

Il computer diventa un nodo con contenuti.

Esempio:

```
              └────────┘
                  │
              Nomad-Net
              /       \
          Phone A    Phone B
```

Il computer non è ancora un gateway.

È semplicemente un **server locale di contenuti**.

Ora aggiungiamo Internet.

Prima:

```

              Wiki
              Mappe
              AI

                │
```

```
                 │

          │   Gateway   │
          │             │
          │ NOMAD NODE │
          └─────────────┘
                 │
             Mesh locale
```

Il computer fa entrambe le cose:

1. contiene servizi locali;
2. collega la rete a Internet.

# Dove entra Project NOMAD?

Solo dopo.

Project NOMAD diventa semplicemente il "cervello dei contenuti":

```
Nomad-Net
    │
    │ richiesta:
    │ content://map/italia
    ▼
Project NOMAD
    │
    ├── Kiwix
    ├── Mappe
    ├── AI locale
    └── Database
```

Nomad-Net non deve sapere **come** viene generato il contenuto.

Deve solo sapere:

> "Esiste un nodo che può fornire questa risorsa?"

# Quindi il percorso corretto senza Raspberry è:

```
1. Mac come primo nodo
        ↓
2. Due nodi software comunicanti
        ↓
3. Routing tra nodi
        ↓
4. Smartphone come client
        ↓
5. Trasferimento contenuti
        ↓
6. Cache locale
        ↓
7. Project NOMAD integrato
        ↓
8. Gateway Internet
        ↓
9. Hardware dedicato (eventuale)
```

Il Raspberry non è il punto di partenza: è solo una possibile evoluzione quando vuoi creare nodi permanenti in luoghi reali (rifugi, scuole, comunità, emergenze).
